An agent credential is a bearer token that lets an AI agent act on exactly one store, in exactly one mode, within an explicit set of scopes. It is a separate credential type from [API keys](/authentication): agent requests are rate limited independently, audited per credential, and subject to the [agentic authorization model](/agentic/authorization).

## Token format

```
spa_live_<48 hex characters>
spa_test_<48 hex characters>
```

The prefix encodes the mode; there is no `X-Livemode` header on agentic endpoints. Only a SHA-256 digest of the token is stored, along with a 16-character prefix used for display. The full token is returned once, at creation.

Agents authenticate with a standard bearer header on every request:

```bash
curl https://api.southpay.io/api/v2/agentic/account \
  -H "Authorization: Bearer spa_test_..."
```

A missing or malformed token returns `401` with code `agent_credential_required`; a token that does not match an active credential returns `401` with code `invalid_agent_credential`. Revoked and expired credentials stop working immediately.

## Scopes

| Scope | Grants |
| --- | --- |
| `payments:read` | Read payments and refunds, wait for payment completion |
| `payments:write` | Create and cancel payments, request refunds |
| `payouts:read` | Read payouts |
| `payouts:write` | Create payouts |
| `assets:read` | Read accepted tokens, balances, payout limits, exchange rates |
| `assets:write` | Enable or disable accepted tokens |
| `x402:read` | Read session mandates and x402 settlements |
| `x402:write` | Issue mandates and create x402 settlements |

A `:write` scope implies the matching `:read`. Omitting `scopes` at creation grants all scopes; pass an explicit array to restrict the credential to least privilege. A request outside the credential's scopes returns `403` with code `insufficient_scope`.

<Note>
  A scope is necessary but not sufficient for money movement. Refunds, token changes, payouts, and mandate issuance are additionally gated by [spend limits and mandates](/agentic/authorization), which deny by default.
</Note>

## Managing credentials

Credentials are managed from the dashboard (**Agents**) or via the merchant API. These endpoints use your dashboard session (JWT plus `X-Store-Id`), not the agent token - the agent cannot manage its own credential.

### Create a credential

<CodeGroup>
```bash Request
curl -X POST https://api.southpay.io/api/v2/agent_credentials \
  -H "Authorization: Bearer <jwt_token>" \
  -H "X-Store-Id: <store_id>" \
  -H "Content-Type: application/json" \
  -d '{
    "agent_credential": {
      "mode": "test",
      "name": "Support bot",
      "agent_principal": "claude@yourcompany.com",
      "scopes": ["payments:read", "payments:write"],
      "expires_at": "2026-12-31T00:00:00Z"
    }
  }'
```

```json Response 201
{
  "id": "01HZ...",
  "token_prefix": "spa_test_4f6a9c1e",
  "mode": "test",
  "livemode": false,
  "name": "Support bot",
  "agent_principal": "claude@yourcompany.com",
  "scopes": ["payments:read", "payments:write"],
  "last_used_at": null,
  "revoked_at": null,
  "expires_at": "2026-12-31T00:00:00.000Z",
  "created_at": "2026-07-12T12:00:00.000Z",
  "secret": "spa_test_4f6a9c1e..."
}
```
</CodeGroup>

<Warning>
  `secret` is the full token and **is only shown once**. Store it in a secrets manager. If it leaks, revoke the credential immediately; there is no way to retrieve it again.
</Warning>

### List, revoke

```bash
curl https://api.southpay.io/api/v2/agent_credentials \
  -H "Authorization: Bearer <jwt_token>" -H "X-Store-Id: <store_id>"

curl -X DELETE https://api.southpay.io/api/v2/agent_credentials/{id} \
  -H "Authorization: Bearer <jwt_token>" -H "X-Store-Id: <store_id>"
```

Listing returns non-revoked credentials (without secrets). `DELETE` revokes; revocation is permanent.

### Activity

Every payment, payout, and x402 settlement records which credential created it. Fetch the most recent 50 of each:

```bash
curl https://api.southpay.io/api/v2/agent_credentials/{id}/activity \
  -H "Authorization: Bearer <jwt_token>" -H "X-Store-Id: <store_id>"
```

```json
{
  "payment_intents":  [ { "id": "...", "reference": "SPX7K2M9", "status": "completed", "settlement_amount": "49.99", "settlement_currency": "USD", "order_id": "ORDER-1042", "created_at": "..." } ],
  "payouts":          [ { "id": "...", "status": "confirmed", "amount_atomic": "25000000", "asset_id": "ETH_USDC", "destination_address": "0x...", "payout_rail": "crypto", "created_at": "..." } ],

```

The same view is available in the dashboard on the credential's **Activity** panel.

## Spend limits

Spend limits are per-credential, per-asset payout caps. They serve two purposes:

1. **They unlock payouts.** Without an authorization provider, an agent cannot pay out an asset at all until a spend limit exists for it (`payout_controls_required`).
2. **They cap payouts.** Once configured, every payout is checked against the per-transaction cap and a daily counter that resets at midnight UTC.

<CodeGroup>
```bash Request
curl -X POST https://api.southpay.io/api/v2/agent_credentials/{id}/spend_limits \
  -H "Authorization: Bearer <jwt_token>" \
  -H "X-Store-Id: <store_id>" \
  -H "Content-Type: application/json" \
  -d '{
    "asset_id": "ETH_USDC",
    "per_tx_cap_atomic": "50000000",
    "daily_cap_atomic": "200000000"
  }'
```

```json Response 200
{
  "id": "01HZ...",
  "asset_id": "ETH_USDC",
  "livemode": false,
  "per_tx_cap_atomic": "50000000",
  "daily_cap_atomic": "200000000"
}
```
</CodeGroup>

Amounts are atomic units of the asset (USDC has 6 decimals, so `50000000` is 50 USDC). Either cap may be null; posting again for the same asset updates the existing limit. `GET .../spend_limits` lists configured limits.

Agents can inspect their own headroom with `GET /agentic/payout_limits` (or the `get_payout_limits` MCP tool), which returns each cap alongside `daily_spent_atomic` and `daily_remaining_atomic` for the current UTC day. See the [API reference](/api-reference/agentic#payout-limits).

## Rate limiting

Agentic endpoints are limited to **120 requests per minute per credential**. Over the limit, requests return `429` with code `rate_limited` in the standard error envelope. The MCP server's `wait_for_payment` tool polls no faster than once per 2 seconds, well inside the limit.
