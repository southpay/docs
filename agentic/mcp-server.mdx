Southpay runs a hosted [Model Context Protocol](https://modelcontextprotocol.io) server that exposes a merchant store as tools any MCP client can call.

```text
https://mcp.southpay.io/mcp
```

It speaks the Streamable HTTP transport at `/mcp`. Each session is backed by its own isolated state, which is where a key set through the `login` tool is held.

The server is a thin proxy over the [agentic REST API](/api-reference/agentic) with no business logic of its own. It holds no secrets: the only credential is the merchant's `spa_` agent key, validated by Southpay on every call. Anything gated on the REST side is gated identically here, and session mandates and x402 settlements are not exposed as tools at all — those are [REST-only](/agentic/x402).

## Connecting

There are three ways to authenticate, resolved in this order per tool call: a key set with `login`, then the session's OAuth-minted key, then the `Authorization` bearer header.

### Bearer key

Send an [agent credential](/agentic/agent-credentials) as a bearer token. A raw `spa_` token skips the OAuth flow entirely.

<CodeGroup>
```bash Claude Code
claude mcp add --transport http southpay https://mcp.southpay.io/mcp \
  --header "Authorization: Bearer spa_test_..."
```

```json Generic MCP config
{
  "mcpServers": {
    "southpay": {
      "url": "https://mcp.southpay.io/mcp",
      "headers": {
        "Authorization": "Bearer spa_live_xxx"
      }
    }
  }
}
```
</CodeGroup>

### Browser login (OAuth)

Connect a client with no token and the server runs an OAuth flow instead. It serves its own metadata discovery, dynamic client registration and token endpoint — which clients like claude.ai require — then forwards you to the Southpay dashboard consent screen, where you pick the store and whether the session is live or test.

On the way back it exchanges the code for an OAuth access token and calls [`POST /api/v2/oauth/agent_credentials`](/agentic/agent-credentials#minting-a-credential-from-an-oauth-token) to mint a scoped `spa_` credential. That credential stays server-side; the MCP client only ever sees tokens issued by the Southpay MCP server.

<Warning>
  One credential exists per application, user, store and mode. Logging in again **rotates that same credential**, which invalidates the key minted by any earlier login. If you have wired a previous login's key into something else, that thing stops working.
</Warning>

### The `login` tool

If a client cannot send custom headers and cannot run OAuth, the agent can call `login` with the key pasted in. It is held for the session until `logout`.

Prefer the bearer header for a live key. A key pasted into `login` passes through the model's context.

## Results and errors

Every tool returns plain JSON as structured content, plus a short human-readable `message`. Failures never raise a protocol error — they come back as data under an `error` key so the agent can read the denial and respond to it:

```json
{
  "error": "southpay_api_error",
  "status": 403,
  "detail": {
    "error": {
      "message": "Agent payouts require a configured authorization provider or a spend limit on this asset",
      "code": "payout_controls_required"
    }
  }
}
```

`detail` carries the API's [error envelope](/agentic/authorization#error-codes) verbatim. Other error values you will see: `not_connected` when no key resolved, `invalid_key` when `login` is given something that does not start with `spa_live_` or `spa_test_`, `login_failed`, `tool_exception`, and `market_data_unreachable` from `research_token`.

Authorization denials (`mandate_required`, `payout_controls_required`, `authorization_denied`) are expected outcomes of the fail-closed design. Explain them; do not retry them.

## Tools

Nineteen tools. Scopes are the agent credential scopes required; a credential limited to `payments:*` is rejected on the token and payout tools. Tools marked **gated** are refused server-side unless a spend limit or an authorization provider permits the action — see [agent authorization](/agentic/authorization).

### Session

| Tool | Parameters | Returns |
| --- | --- | --- |
| `login` | `api_key` | `{logged_in: true, account}`, or `{error: "invalid_key"}` if it does not start with `spa_live_` / `spa_test_` |
| `logout` | none | `{logged_out}` — `true` if a pasted key existed |

### Account

| Tool | Parameters | Scope | Returns |
| --- | --- | --- | --- |
| `get_account` | none | any | Store id, name and KYC status; `mode` and `livemode`; the credential's name, principal, token prefix, scopes, last use and expiry; the authorization provider in effect and whether mandates are required; the accepted-asset count |

Call this first. `authorization.mandates` tells you whether the gated tools can succeed at all on this store.

### Payments

| Tool | Parameters | Scope | Returns |
| --- | --- | --- | --- |
| `create_payment` | `amount` (decimal string, ≤ 2 places), `currency` (default `"USD"`), `order_id?`, `metadata?` (≤ 50 keys, string values) | `payments:write` | `{id, status, reference, settlement_amount, settlement_currency, order_id, hosted_url, expires_at, deposit_addresses[]}` |
| `get_payment` | `payment_id` | `payments:read` | Same summarized shape |
| `list_payments` | `page` (default 1), `per_page` (default 10, max 100), `reference?` | `payments:read` | `{payments[], meta}` |
| `wait_for_payment` | `payment` (id or reference), `timeout_seconds` (default 60, clamped 1–240), `poll_interval_seconds` (default 3, minimum 2) | `payments:read` | `{done: true, status, polls, payment}` or `{done: false, timed_out: true, status, polls, hint, payment}` |
| `cancel_payment` | `payment_id` | `payments:write` | The canceled payment |
| `refund_payment` | `payment_id`, `amount?`, `asset_id?` | `payments:write` | The created refunds. **Gated** |
| `list_refunds` | `payment_id` | `payments:read` | Refunds for the payment, newest first |

Each entry in `deposit_addresses[]` is `{address, crypto_amount, crypto_amount_atomic, coin_symbol, chain_symbol, asset_id, exchange_rate}`. `crypto_amount` is the tool's own human rendering of `crypto_amount_atomic` at the asset's decimals; it is not a field the REST API returns.

`create_payment`, `refund_payment` and `create_payout` send an `Idempotency-Key` per call, generated by the server.

`wait_for_payment` holds the request open, so keep the budget modest and call again rather than asking for the full 240 seconds. It accepts a reference as well as an id: on a 404 it retries the lookup as a reference filter. For durable notification across sessions, configure a [webhook](/webhooks) instead.

Omit `amount` on `refund_payment` for a full refund; a decimal string gives a partial refund, and partial refunds apply to completed payments only. `asset_id` is only needed when a payment settled in more than one asset.

### Tokens and balances

| Tool | Parameters | Scope | Returns |
| --- | --- | --- | --- |
| `list_tokens` | none | `assets:read` | `{accepted[], available[]}`, each `{asset_id, coin_symbol, chain_symbol, active}` |
| `get_balance` | `asset_id?` | `assets:read` | `{balances: [{asset_id, coin_symbol, chain_symbol, atomic_decimals, balance_atomic, balance}], settlement_balance: {currency, amount_cents, amount}}` |
| `set_token` | `asset_id`, `active` (boolean) | `assets:write` | `{asset_id, active, provider}`. **Gated** |

`balance` and `amount` are the tool's decimal renderings of `balance_atomic` and `amount_cents`. `settlement_balance` is the store-wide value of stablecoin holdings in the store's settlement currency, and stays store-wide even when `asset_id` narrows the balance list. `amount_cents` is `null` if the rate lookup fails.

The accepted and available lists are filtered to the credential's mode, so a test credential sees testnet assets only.

### Payouts

| Tool | Parameters | Scope | Returns |
| --- | --- | --- | --- |
| `create_payout` | `asset_id`, `amount_atomic` (positive integer), `destination_address` | `payouts:write` | The created payout. **Gated** |
| `get_payout` | `payout_id` | `payouts:read` | Payout detail |
| `list_payouts` | `page` (default 1), `per_page` (default 25, max 100) | `payouts:read` | `{data[], pagination}` |
| `get_payout_limits` | `asset_id?` | `assets:read` | `{limits[], utc_day}` |

Each row in `limits[]` carries `asset_id`, `coin_symbol`, `chain_symbol`, `atomic_decimals`, `per_tx_cap_atomic`, `daily_cap_atomic`, `daily_spent_atomic`, `daily_remaining_atomic` and `controls_configured`, plus decimal renderings as `per_tx_cap`, `daily_cap`, `daily_spent` and `daily_remaining`.

Call `get_payout_limits` before `create_payout`. `controls_configured: false` on an asset means a payout in it will be denied with `payout_controls_required`, and staying inside `daily_remaining` avoids a `daily_cap_exceeded` denial. `amount_atomic` is base units — wei for ETH — so confirm the figure with a human before spending it.

### Rates and market data

| Tool | Parameters | Scope | Returns |
| --- | --- | --- | --- |
| `get_exchange_rate` | `asset_id?`, `currency?` | `assets:read` | `{currency, rates: [{asset_id, coin_symbol, chain_symbol, currency, rate, source}]}` |
| `research_token` | `symbol_or_id`, `vs_currency` (default `"usd"`) | none | `{query, coin_id, vs_currency, price, market_cap, volume_24h, change_24h_pct, source}` |

`get_exchange_rate` is Southpay's own rate, the one applied when pricing a payment. `currency` defaults to the store's settlement currency and must be one of the ten accepted payment currencies. Omit `asset_id` for every accepted asset.

`research_token` is public CoinGecko data proxied through Southpay's cached [market data endpoint](/api-reference/agentic). It touches no store data and no funds, and needs no credential. Accepts a ticker such as `"ETH"` or a CoinGecko id such as `"ethereum"`. Use `get_exchange_rate`, not this, for the rate a customer will be charged.

## Picking up tool changes

Deploying the server updates it immediately, but MCP clients cache the tool list for the life of a session. The server advertises `listChanged`, and a fresh chat or re-added connector is the reliable way to see new tools.

## Isolation

Tools only ever see the store and mode encoded in the credential. Payments, payouts, refunds and settlements are further scoped to the credential that created them, so an agent cannot read or cancel another integration's payments on the same store. Agents cannot manage credentials, their own included.
