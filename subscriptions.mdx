---
title: "Subscriptions"
description: "Bill customers on a recurring schedule with products, prices, and subscription items, collected on-chain each cycle."
---

Subscriptions let you charge a customer repeatedly on a fixed schedule. Southpay generates an invoice at the start of every cycle and collects it through the same crypto checkout used for [one-off payments](/payment-intents), so a subscription is really an automatic invoice generator.

## Building blocks

You compose a subscription from four resources. See the [Recurring API reference](/api-reference/recurring) for full field shapes, and [Invoicing](/api-reference/invoicing) for customers.

| Resource | What it is |
| --- | --- |
| **Customer** | The billed party. Reused across invoices and subscriptions. |
| **Product** | Something you sell (a plan, an add-on). |
| **Price** | An amount, currency, and interval attached to a product. A price is reusable across any number of customers. |
| **Subscription** | Bills one customer on a price's interval. Made of one or more **items**. |

A price sets `interval` (`daily`, `weekly`, `monthly`, or `yearly`) and `interval_count` — set `interval_count: 3` on a monthly price for quarterly billing. Money fields are immutable once a price exists; archive and create a new one to change them.

## Items

A subscription is billed as one or more items, each pairing a price with a quantity. The first item is the anchor: its price sets the interval and currency for the whole subscription. Add more items for a base plan plus add-ons, and every item becomes a line on the same invoice.

```text
Subscription
 ├── Item → Pro plan      ($29 / month × 1)
 └── Item → Extra seats   ($5 / month × 3)

Invoice each month:
  Pro plan       $29.00
  Extra seats    $15.00
  Total          $44.00
```

All items must share the same interval, interval count, and currency.

## Create a subscription

Pick a customer and one or more `{ price_id, quantity }` items.

```bash
POST /api/v2/billing/subscriptions
Authorization: Bearer sp_test_YOUR_KEY
Content-Type: application/json
```

```json
{
  "subscription": {
    "customer_id": "7b3f9d02-1c48-4ea6-95f7-0d21c6b48e93",
    "items": [
      { "price_id": "a4c81e57-9026-4b3d-8f14-6e05b7c92d38", "quantity": 1 },
      { "price_id": "e91d0472-53ba-4c68-90af-2d7e14c8b605", "quantity": 3 }
    ],
    "trial_period_days": 14,
    "grace_cycles": 1
  }
}
```

Every id is a bare UUID. For a single price, use the shorthand `"price_id"` (with an optional `"quantity"`) instead of `items`.

<Warning>
Billing endpoints **ignore the `Idempotency-Key` header entirely.** Retrying a subscription or customer create after a timeout can produce a duplicate. Deduplicate on your side, or check for an existing record before retrying. See [Idempotency](/idempotency#where-the-header-applies).
</Warning>

To subscribe several customers to the same plan, create one subscription per customer with the same `items` — a price is shared, a subscription is per-customer.

## Trials

Set `trial_period_days` to start the subscription in a `trialing` status. No invoice is issued during the trial; when it ends, the subscription becomes `active` and its first cycle is billed.

## The billing cycle

At the start of each cycle Southpay creates and finalizes an invoice for every item, then advances the period. The customer pays the invoice on-chain, exactly like a one-off payment. Listen for `invoice.finalized` (a new cycle was billed) and `invoice.paid` (the customer paid) rather than polling.

You can list a subscription's invoices with `GET /billing/invoices?subscription_id=...`. That endpoint is paginated inside a `meta` envelope.

<Note>
`GET /billing/subscriptions` is **not** paginated. It returns the whole filtered collection as a bare array, with no `meta` and no `pagination` key. Filters are `status` and `customer_id`. Do not write a pager against it, and do not assume the response is an object.
</Note>

## Manage the lifecycle

| Status | Meaning |
| --- | --- |
| `trialing` | In a free trial; bills its first cycle at trial end. |
| `active` | Billing normally. |
| `past_due` | A cycle invoice was not paid in time. |
| `paused` | Billing suspended; resume to continue. |
| `canceled` | Ended (terminal). |

- **Change the plan** — `PATCH /billing/subscriptions/:id` with a new `items` set. The change applies from the next cycle; there is no mid-cycle proration.
- **Cancel** — `POST .../cancel` ends it immediately, or pass `{ "at_period_end": true }` to let the current cycle finish first. Undo a scheduled cancellation with `POST .../uncancel`.
- **Pause / resume** — `POST .../pause` suspends billing; `POST .../resume` restarts it from a fresh period.

If a cycle goes unpaid, the subscription moves to `past_due` and Southpay emits `subscription.past_due`. Once the grace window (about `grace_cycles` × the interval) is exhausted, the invoice is marked uncollectible and the subscription is canceled for non-payment.

## Webhooks

Subscribe to the [billing webhook events](/webhooks#billing-events): `subscription.created`, `subscription.updated`, `subscription.past_due`, `subscription.canceled`, plus the `invoice.*` events that carry each renewal and payment.
