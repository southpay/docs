A webhook endpoint is a URL Southpay `POST`s signed JSON to when something changes on your store. You register the URL, name every event you want, store the signing secret, and verify each delivery before acting on it.

## Register an endpoint

<CodeGroup>
```bash Request
curl -X POST https://api.southpay.io/api/v2/webhook_endpoints \
  -H "Authorization: Bearer sp_sk_test_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "webhook_endpoint": {
      "url": "https://yourapp.example/webhooks/southpay",
      "description": "Order fulfillment handler",
      "subscribed_events": [
        "payment_intent.completed",
        "payment_intent.failed",
        "payment_intent.expired",
        "payment_intent.refunded"
      ]
    }
  }'
```

```json Response 201
{
  "id": "b7e4c210-5d83-4f16-9c02-6ea1f3d85b47",
  "url": "https://yourapp.example/webhooks/southpay",
  "description": "Order fulfillment handler",
  "status": "active",
  "subscribed_events": [
    "payment_intent.completed",
    "payment_intent.failed",
    "payment_intent.expired",
    "payment_intent.refunded"
  ],
  "signing_secret": "whsec_4f8b1c2d...",
  "delivery_success_rate": null,
  "created_at": "2026-08-07T14:01:00.000Z"
}
```
</CodeGroup>

<Warning>
`signing_secret` appears **only** in the create response and in the response to `rotate_secret`. Every other read returns `signing_secret_preview`, the first twelve characters. Store the full value before you close the terminal.
</Warning>

Requires the `webhooks:write` scope. The endpoint id is a bare UUID — there is no `we_` prefix scheme anywhere in this API.

### subscribed_events is required, and literal

`subscribed_events` must be a non-empty array of exact event names from the [catalogue](#event-catalogue). It is validated as a strict subset, and matching at dispatch time is literal array containment.

**Wildcards are not supported.** `"*"` fails validation. So does `"payment_intent.*"`. A merchant who wants everything must enumerate all 23 names. Omitting the field entirely yields an empty array, which then fails the presence check with `422` and a `{"errors": [...]}` body.

<Note>
If you create a second endpoint with the same `platform` value (`shopify`, `woocommerce`, `prestashop`, `magento`) in the same mode, Southpay does not return a conflict. It adopts the existing row, rotates its secret, and returns `200` with the new `signing_secret`. The old secret stops working immediately. This is how plugin reinstalls are meant to work; it is surprising if you hit it by accident.
</Note>

## The envelope

```json
{
  "id": "d31a5c88-9b74-4c02-b6ff-7e2a4d190c65",
  "type": "payment_intent.completed",
  "created": 1786125600,
  "livemode": true,
  "api_version": "2026-04-14",
  "data": {
    "object": {
      "id": "K4TP9WQZ2XR7HB3M",
      "status": "completed",
      "settlement_amount_cents": 4999,
      "settlement_currency": "USD",
      "from_status": "processing",
      "to_status": "completed",
      "metadata": { "order_id": "order_8721" }
    }
  }
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string (UUID) | The event id. Deduplicate on this. |
| `type` | string | See the [catalogue](#event-catalogue) |
| `created` | integer | Unix seconds |
| `livemode` | boolean | `false` for test-mode events |
| `api_version` | string | Always the literal `"2026-04-14"` |
| `account` | string (UUID) | **Only** on events fanned out to a [platform](/platform-accounts) about a sub-merchant. Absent on your own events, so you can route on its presence. |
| `data.object` | object | The payload. Shape depends on the event family. |

There is no top-level `"object": "event"` key.

<Warning>
For payment and transaction events, `data.object` has exactly seven keys: `id`, `status`, `settlement_amount_cents`, `settlement_currency`, `from_status`, `to_status`, `metadata`.

**`id` holds the payment intent's `reference`, not its UUID.** There is no `reference` key. There is no `settlement_amount` key — the amount is an integer in minor units under `settlement_amount_cents`.
</Warning>

Billing events are different. `invoice.*` and `subscription.*` serialize the full detail view of the invoice or subscription into `data.object`, so you get line items, customer, period boundaries and every other field rather than the seven-key summary. `store.verification.*` events use a freshly generated UUID as the envelope `id` and carry the store's verification state.

<Note>
`api_version` is stamped from a constant, not from the `api_version` column on your endpoint. Changing that column has no effect on what you receive. Treat the field as informational.
</Note>

## Headers

| Header | Value |
| --- | --- |
| `Southpay-Signature` | `t=<unix seconds>,v1=<hex digest>` |
| `Southpay-Delivery-Id` | UUID of this delivery |
| `Content-Type` | `application/json` |
| `User-Agent` | `Southpay-Webhooks/1.0` |

## Verifying the signature

1. Split `Southpay-Signature` on `,` into `t` and `v1`.
2. Build the signed string `"{t}.{raw request body}"`.
3. Compute `HMAC-SHA256` over it, keyed with the signing secret, and hex-encode it.
4. Compare to `v1` with a timing-safe comparison.

<Warning>
Two details break most first attempts.

**Use the raw body bytes.** Parsing JSON and re-serializing it changes whitespace and key order, and the digest will not match.

**Use the secret exactly as issued, `whsec_` prefix included.** It is the literal UTF-8 string that keys the HMAC. Do not strip the prefix and do not base64-decode it.
</Warning>

Southpay does **not** enforce a timestamp tolerance on outbound deliveries — it only stamps `t`. If you want replay protection, reject deliveries whose `t` is more than a few minutes old. That is your decision to make, not something the API does for you.

<CodeGroup>
```typescript server/webhook.ts
import express from "express";
import { createHmac, timingSafeEqual } from "node:crypto";

const TOLERANCE_SECONDS = 300;

export function verify(rawBody: Buffer, header: string, secret: string): boolean {
  const parts = Object.fromEntries(
    header.split(",").map(p => p.split("=", 2) as [string, string])
  );
  if (!parts.t || !parts.v1) return false;

  const age = Math.floor(Date.now() / 1000) - Number(parts.t);
  if (!Number.isFinite(age) || Math.abs(age) > TOLERANCE_SECONDS) return false;

  const computed = createHmac("sha256", secret)
    .update(`${parts.t}.${rawBody.toString("utf8")}`)
    .digest("hex");

  const a = Buffer.from(computed);
  const b = Buffer.from(parts.v1);
  return a.length === b.length && timingSafeEqual(a, b);
}

const app = express();

app.post(
  "/webhooks/southpay",
  express.raw({ type: "application/json" }),
  (req, res) => {
    const sig = req.headers["southpay-signature"] as string | undefined;
    if (!sig || !verify(req.body, sig, process.env.SOUTHPAY_WEBHOOK_SECRET!)) {
      return res.status(401).end();
    }

    const event = JSON.parse(req.body.toString());
    res.json({ received: true });
    queue.enqueue("southpay_event", event);
  }
);
```

```python server/webhook.py
import hashlib
import hmac
import os
import time

from flask import Flask, jsonify, request

app = Flask(__name__)
TOLERANCE_SECONDS = 300


def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    timestamp, v1 = parts.get("t"), parts.get("v1")
    if not timestamp or not v1:
        return False

    if abs(int(time.time()) - int(timestamp)) > TOLERANCE_SECONDS:
        return False

    computed = hmac.new(
        secret.encode(),
        f"{timestamp}.{raw_body.decode()}".encode(),
        hashlib.sha256,
    ).hexdigest()
    return hmac.compare_digest(computed, v1)


@app.post("/webhooks/southpay")
def webhook():
    sig = request.headers.get("Southpay-Signature", "")
    if not verify(request.data, sig, os.environ["SOUTHPAY_WEBHOOK_SECRET"]):
        return jsonify(error="Invalid signature"), 401

    enqueue("southpay_event", request.get_json())
    return jsonify(received=True)
```

```go server/webhook.go
package webhook

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
	"time"
)

const toleranceSeconds = 300

func Verify(rawBody []byte, header, secret string) bool {
	parts := map[string]string{}
	for _, p := range strings.Split(header, ",") {
		if kv := strings.SplitN(p, "=", 2); len(kv) == 2 {
			parts[kv[0]] = kv[1]
		}
	}

	ts, v1 := parts["t"], parts["v1"]
	if ts == "" || v1 == "" {
		return false
	}

	sent, err := strconv.ParseInt(ts, 10, 64)
	if err != nil || abs(time.Now().Unix()-sent) > toleranceSeconds {
		return false
	}

	mac := hmac.New(sha256.New, []byte(secret))
	fmt.Fprintf(mac, "%s.%s", ts, rawBody)
	return hmac.Equal([]byte(hex.EncodeToString(mac.Sum(nil))), []byte(v1))
}

func abs(n int64) int64 {
	if n < 0 {
		return -n
	}
	return n
}
```

```ruby app/services/southpay_webhook.rb
require "openssl"

module SouthpayWebhook
  TOLERANCE_SECONDS = 300

  def self.verify(raw_body, header, secret)
    parts = header.to_s.split(",").map { |p| p.split("=", 2) }.to_h
    timestamp = parts["t"]
    v1 = parts["v1"]
    return false unless timestamp && v1
    return false if (Time.now.to_i - timestamp.to_i).abs > TOLERANCE_SECONDS

    computed = OpenSSL::HMAC.hexdigest("sha256", secret, "#{timestamp}.#{raw_body}")
    ActiveSupport::SecurityUtils.secure_compare(computed, v1)
  end
end
```

## Event catalogue

Twenty-three names pass `subscribed_events` validation. Eighteen of them are emitted.

### Payment intent events

| Event | Fires when |
| --- | --- |
| `payment_intent.created` | An intent is created |
| `payment_intent.processing` | A transaction for one of its deposit addresses is confirming or confirmed |
| `payment_intent.completed` | Enough confirmed funds arrived and the balance is credited |
| `payment_intent.failed` | Funds arrived but the amount rules were not met |
| `payment_intent.expired` | The 60-minute window closed, or an agent canceled a pending intent |
| `payment_intent.refunded` | A refund confirmed on-chain |

Read `data.object.status` and, where you need the reason, fetch the intent for its `state_reason`. See [Payment lifecycle](/payment-lifecycle).

### Transaction events

| Event | Fires when |
| --- | --- |
| `transaction.confirming` | A deposit transaction is seen and awaiting confirmations |
| `transaction.confirmed` | It reached the chain's required confirmation count |
| `transaction.failed` | It failed on-chain |

### Billing events

Emitted only for stores using [invoicing](/api-reference/invoicing) and [subscriptions](/subscriptions). `data.object` is the full resource, not the seven-key summary.

| Event | Fires when |
| --- | --- |
| `invoice.finalized` | An invoice is finalized and payable. A subscription renewal produces one per cycle. |
| `invoice.paid` | An invoice is paid in full |
| `invoice.voided` | An invoice is voided |
| `subscription.created` | A subscription is created |
| `subscription.updated` | Items, quantity, pause, resume, or scheduled cancellation changed |
| `subscription.past_due` | A cycle invoice went unpaid past its grace window |
| `subscription.canceled` | A subscription ended |

### Verification events

| Event | Fires when |
| --- | --- |
| `store.verification.approved` | A store passed verification and can transact |
| `store.verification.rejected` | Verification was refused. `data.object.rejection_reason` says why. |

Most useful to [platforms](/platform-accounts) tracking sub-merchant onboarding.

## Events that never arrive

The catalogue above lists eighteen events. Five more pass validation and do nothing.

<Warning>
**Five event names pass validation but are never emitted.** Nothing in the API creates a delivery for any of them. If you subscribe, you will wait forever and no error will tell you so.

- `payout.created`
- `payout.confirmed`
- `payout.failed`
- `fee_sweep.confirmed`
- `fee_sweep.failed`

Payout lifecycle is not published over webhooks today. **Poll `GET /api/v2/payouts` or `GET /api/v2/payouts/{id}`** and read `status` and `state_transitions`. If you already have a subscription to any of these names, it is safe to leave in place and safe to remove — it has never delivered anything either way.
</Warning>

## Events you cannot receive

The reverse problem exists too. Four event types are produced internally but cannot appear in `subscribed_events`, so no endpoint ever matches them and they are dropped:

`payment_intent.canceled`, `payment_intent.underpaid_detected`, `transaction.pending`, `transaction.submitted`.

The one that catches people out is `payment_intent.canceled`, emitted when an [agent](/agentic/index) cancels a pending intent. Watch for `payment_intent.expired` and check for `state_reason: "canceled_by_agent"` on the intent instead.

## Delivery and retries

| Property | Value |
| --- | --- |
| Success | Any `2xx` |
| Connect timeout | 5 seconds |
| Read timeout | 30 seconds |
| Maximum attempts | 10 |
| Total window | Roughly 18 hours |

<Warning>
**Every non-`2xx` response is retried**, including `400`, `401`, `403` and `404`. There is no "client errors are not retried" rule. A handler that returns `400` on a payload it does not recognise will be hammered ten times over eighteen hours for every such event.

Return `2xx` for events you choose to ignore. Reserve non-`2xx` for "I could not process this and I want it again".
</Warning>

Retries back off on this schedule: 30 seconds, 2 minutes, 5 minutes, 10 minutes, 30 minutes, 1 hour, 2 hours, 5 hours, 10 hours. After the tenth failed attempt the endpoint flips to `status: "error"` and the store owner is emailed.

<Note>
While an endpoint is not `active` — disabled by you, or flipped to `error` — queued deliveries are dropped rather than held. Re-enabling the endpoint does not replay them. Use `redeliver` for anything you need back.
</Note>

Deliveries are also refused before they leave if the URL resolves to a private, loopback, link-local or unique-local address. The delivery is marked `failed` and the endpoint flips to `error`. Tunnel to a public hostname when testing locally.

### Deduplication

Delivery is at-least-once. Southpay keys each delivery internally on `(endpoint, event)`, which prevents most duplicates, but a retry can still repeat a delivery your handler already processed and acknowledged slowly. Guard on the envelope `id`.

```typescript
const claimed = await db.processedEvents.insertIfAbsent(event.id);
if (!claimed) return res.json({ received: true });

await fulfill(event);
```

Claim the id before doing the work, not after, or two concurrent retries can both pass the check.

## Managing an endpoint

| Operation | Request |
| --- | --- |
| List | `GET /api/v2/webhook_endpoints` |
| Read, with recent deliveries and the full event list | `GET /api/v2/webhook_endpoints/{id}` |
| Update `url`, `description`, `subscribed_events`, `metadata` | `PATCH /api/v2/webhook_endpoints/{id}` |
| Delete (soft) | `DELETE /api/v2/webhook_endpoints/{id}` → `204` |
| Disable / enable | `PATCH /api/v2/webhook_endpoints/{id}/disable` / `/enable` |
| Send a test event | `POST /api/v2/webhook_endpoints/{id}/send_test` |
| Redeliver one delivery | `POST /api/v2/webhook_endpoints/{id}/redeliver` |
| Rotate the secret | `POST /api/v2/webhook_endpoints/{id}/rotate_secret` |

`send_test` takes an optional `event_type`. It defaults to your first subscribed event, falling back to `payment_intent.completed`. An unknown name returns `422 "Unknown event type"`.

`redeliver` takes `delivery_id`, in the query string or the JSON body. Delivery ids come from `recent_deliveries` on the endpoint read.

```bash
curl -X POST "https://api.southpay.io/api/v2/webhook_endpoints/{id}/redeliver" \
  -H "Authorization: Bearer sp_sk_test_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"delivery_id": "1c9f0b7a-2d84-4e33-9a61-0f5c8d2b7e40"}'
```

### Rotating the secret

`POST /api/v2/webhook_endpoints/{id}/rotate_secret` returns the endpoint with a new `signing_secret`.

<Danger>
Rotation is an immediate hard cutover. **There is no overlap window and no dual-signing period.** The moment the request returns, every delivery is signed with the new secret and the old one verifies nothing — including deliveries already queued and retries of older events.

Deploy so that the new secret is live before you rotate: read the secret from a store your running processes re-read, rotate, then confirm. Rotating first and deploying second guarantees a gap of failed verifications, and those failures are retried as non-`2xx` for eighteen hours.
</Danger>

## Endpoint fields

| Field | Notes |
| --- | --- |
| `id` | Bare UUID |
| `url` | Must be HTTPS and publicly resolvable |
| `status` | `active`, `disabled`, `error` |
| `subscribed_events` | Literal list. No wildcards. |
| `signing_secret_preview` | First twelve characters, followed by `...` |
| `delivery_success_rate` | Percentage to one decimal place, or `null` with no deliveries |
| `platform` | `woocommerce`, `prestashop`, `shopify`, `magento`, `custom` |
| `api_version` | Stored but not used when building payloads |
| `recent_deliveries[]` | On the single-endpoint read: `id`, `event_type`, `status`, `attempts`, `response_status`, `delivered_at`, `created_at` |

Delivery `status` values are `pending`, `attempting`, `delivered`, `failed`, `ignored`.

## Platform fan-out

If you are a [platform](/platform-accounts), payment, transaction and store-verification events for your sub-merchants are delivered to your endpoints as well as theirs, with a top-level `account` field naming the sub-merchant.

**Billing events do not fan out.** An invoice or subscription event on a sub-merchant reaches that merchant's endpoints only.
