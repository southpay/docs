A refund sends crypto back on-chain, by default to the address the customer paid from. Refunds always belong to a payment intent. One request can produce several refund records — one per asset the intent received — so both endpoints return an array.

Amounts you send are decimal major units of the crypto asset. Amounts you read back are atomic-unit strings: `decimal = atomic / 10^atomic_decimals`.

Paths are relative to `https://api.southpay.io/api/v2`.

## Authentication and scope

`GET` requires `refunds:read`, `POST` requires `refunds:write`. Note that this is a different resource from `payments`, even though the path is nested under a payment intent — a key holding only `payments:write` cannot refund.

Agents use a separate endpoint with different error semantics. See [Agentic API](/api-reference/agentic#refund-a-payment).

## Where refunds come from

**Automatic.** When a payment is rejected — overpaid on a store that does not accept overpayments, or underpaid past expiry on a store that does not accept underpayments — Southpay refunds the confirmed funds itself. These carry `reason` `failed_overpaid` or `failed_underpaid`.

**Requested.** You call `POST /payments/{id}/refunds`. These carry `reason` `merchant_requested`.

## List refunds for a payment intent

**`GET /payments/{payment_intent_id}/refunds`** — scope `refunds:read`.

Returns a **bare array**, newest first. No envelope, no pagination.

## Request a refund

**`POST /payments/{payment_intent_id}/refunds`** — scope `refunds:write`. `Idempotency-Key` is **required**.

An intent is refundable while its status is `completed`, `failed` or `expired` and it still holds confirmed funds that have not already been refunded.

All fields go inside an optional `refund` object. Sending them at the top level also works.

<ParamField body="refund.amount" type="string">
  Decimal amount in major units of the asset. Omit to refund the full remaining balance. Only valid for `completed` intents.
</ParamField>

<ParamField body="refund.asset_id" type="string">
  Restrict the refund to one asset when the intent received several. Required alongside `amount` or `destination_address` in that case.
</ParamField>

<ParamField body="refund.destination_address" type="string">
  Send the refund somewhere other than the address the customer paid from. Must be valid for the asset's chain and must not be a Southpay deposit address.
</ParamField>

<Warning>
On-chain transfers are irreversible. A `destination_address` typo sends real funds to an address nobody controls. Verify it before you send.
</Warning>

<CodeGroup>
```bash Request
curl -X POST https://api.southpay.io/api/v2/payments/7b1f0c2e-2b0a-4c31-9f0e-1d2c3b4a5e6f/refunds \
  -H "Authorization: Bearer sp_sk_test_…" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: refund_order_1043" \
  -d '{ "refund": { "amount": "10.00", "asset_id": "ETH_USDC" } }'
```

```json Response 201
[
  {
    "id": "9e7d6c5b-4a39-4281-b7c6-d5e4f3a2b109",
    "status": "pending",
    "reason": "merchant_requested",
    "destination_address": "0x1234…",
    "amount_atomic": "10000000",
    "tx_hash": null,
    "attempts": 0,
    "asset_id": "ETH_USDC",
    "coin_symbol": "USDC",
    "chain_symbol": "ETH",
    "atomic_decimals": 6,
    "created_at": "2026-05-12T12:00:00.000Z",
    "updated_at": "2026-05-12T12:00:00.000Z"
  }
]
```
</CodeGroup>

<Note>
`amount` and `asset_id` selection apply only to `completed` intents. For `failed` or `expired` intents the endpoint refunds the full confirmed balance across every asset, and sending `amount` returns `422`.
</Note>

### Idempotency behaviour

Your `Idempotency-Key` is not used verbatim. Southpay derives a per-asset key from it, so a payment that received two assets produces two refund records under one key you sent. Replaying the same key returns the existing refunds — still with status `201`, not `200`.

For `failed` and `expired` intents the response contains **every** refund on the intent, not only the ones this call created.

If an earlier refund already `failed`, sending a new `destination_address` starts a fresh attempt to that address. While a refund is `pending` or `submitted`, the existing record is returned instead of a second one being created.

## Refund lifecycle

| Status | Terminal | Meaning |
| --- | --- | --- |
| `pending` | No | Created, queued for broadcast. |
| `submitted` | No | Broadcast, awaiting confirmations. |
| `confirmed` | Yes | Confirmed on-chain. |
| `failed` | Yes | Could not be completed. Ledger entries are reversed. |

When a refund reaches `confirmed`, its payment intent moves to `refunded` with `state_reason: "refund_completed"` and fires `payment_intent.refunded`. Subscribe to that [webhook](/webhooks) rather than polling.

## Errors

Every failure on this endpoint returns `422` with the flat envelope `{"error": "<message>"}`. The value is the human-readable sentence below — **not** a machine code and **not** a Ruby class name.

| Message | Cause |
| --- | --- |
| `Idempotency-Key header is required` | Header missing. |
| `Payment in status 'pending' is not refundable` | Status is not `completed`, `failed` or `expired`. |
| `No confirmed funds available to refund` | Nothing confirmed, or everything already refunded. |
| `Partial refunds are only supported for completed payments` | `amount` sent for a `failed` or `expired` intent. |
| `Refund amount '10.x' is not a valid number` | `amount` is not parseable. |
| `Refund amount 10.0 is invalid; 5.0 refundable for asset 'ETH_USDC'` | `amount` exceeds the remaining refundable balance. |
| `No confirmed payment found for asset 'ETH_USDT'` | `asset_id` does not match any confirmed deposit. |
| `Payment has confirmed funds in multiple assets; specify asset_id` | Partial refund on a multi-asset intent without `asset_id`. |
| `Payment has confirmed funds in multiple assets; specify asset_id when overriding the destination` | `destination_address` on a multi-asset intent without `asset_id`. |
| `Payment has confirmed funds in multiple assets; a single destination override cannot apply to all of them` | Destination override cannot be resolved to one asset. |
| `Destination override matches a Southpay deposit address` | The override is one of ours. |
| `Refund destination resolves to own deposit address` | The customer's source address is a Southpay address. |
| `Refund destination address failed format validation for ETH` | Malformed address for that chain. |
| `No source address on confirmed transaction` | No sender recorded and no override supplied. |
| `Refund exceeds merchant ledger balance for intent …` | Your ledger balance for the asset is short. |

A `404` for an unknown payment intent comes from the global handler and uses the *structured* envelope instead: `{"error": {"message": "…", "code": null}}`. Handle both shapes.

<Note>
Only the agentic refund endpoint returns machine-readable codes — `not_refundable`, `nothing_to_refund`, `invalid_amount`, `asset_not_found`, `ambiguous_asset`, `invalid_destination`, `insufficient_balance`. This endpoint returns the message text only, so match on status code and endpoint, never on the string.
</Note>
