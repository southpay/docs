---
title: "Reconciliation"
description: "Answer the questions a fintech team actually asks: why is this balance what it is, what changed it, and does it match the outside world."
---

Reconciliation is the real problem most fintech teams are solving when they reach for a ledger. The questions are concrete and they come from finance, support, and engineering at once:

- Why is this balance 1023.17?
- Which transaction changed it?
- What happened between date X and date Y?
- Does it match an external system, such as an external processor or your bank statement?

This page answers each question with the same primitives you already use to write. Because balances are derived from postings and history is append-only, every answer traces back to durable records you can fetch.

## Why is this balance 1023.17?

A balance is not a stored number that someone could have edited. It is derived from the account's postings, so you can always open it up and see the entries that produced it.

List the postings on the account:

```bash
curl "https://ledger.southpay.io/api/v1/accounts/cash:usd/postings" \
  -H "Authorization: Bearer $TOKEN"
```

For a period view with opening and closing balances around the same postings, use the account statement:

```bash
curl "https://ledger.southpay.io/api/v1/accounts/cash:usd/statement?from=2026-04-01T00:00:00Z&to=2026-05-01T00:00:00Z" \
  -H "Authorization: Bearer $TOKEN"
```

The statement returns the opening balance at `from`, every posting in the window ordered by `value_date`, and the closing balance at `to`. The opening balance plus the postings always equals the closing balance, so the number is never a mystery.

## Which transaction changed it?

Every posting belongs to exactly one transaction. The postings list and the account statement both carry the transaction reference for each entry, so you can go from "this line moved the balance" to "this transaction caused it" in one hop.

Fetch the transaction to see all of its legs, its metadata, and any reversal links:

```bash
curl "https://ledger.southpay.io/api/v1/transactions/{id}" \
  -H "Authorization: Bearer $TOKEN"
```

Because corrections are new transactions rather than edits, a reversed or refunded transaction still shows in history with its `reverses` and `reversed_by` links intact. Nothing disappears.

## What happened between date X and Y?

The account statement is the per-account answer. It bounds the postings by `value_date`, so a point-in-time question gets a point-in-time answer: the result is computed from when each movement was economically effective, not from when the row was inserted.

```bash
curl "https://ledger.southpay.io/api/v1/accounts/cash:usd/statement?from=2026-04-01T00:00:00Z&to=2026-04-15T00:00:00Z" \
  -H "Authorization: Bearer $TOKEN"
```

For a tenant-wide, replayable view of everything that changed, read the durable events tail:

```bash
curl "https://ledger.southpay.io/api/v1/events" \
  -H "Authorization: Bearer $TOKEN"
```

Every successful write emits an event, and the events list is replayable, so a consumer that fell behind can catch up without gaps. Together the statement (per account) and the events tail (tenant-wide) cover both "what did this account do?" and "what did the whole ledger do?" over a window.

## Does it match an external system?

This is reconciliation proper: comparing your ledger against an external source of truth, such as an external processor or your bank statement. You bring a snapshot of external items, and the ledger matches them against your unreconciled postings.

```bash
curl -X POST "https://ledger.southpay.io/api/v1/reconciliation_runs" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "source": "acme_processor",
        "external_reference": "acme:2026-05-14",
        "from": "2026-05-14T00:00:00Z",
        "to": "2026-05-15T00:00:00Z",
        "items": [
          { "external_id": "ext_abc", "amount": 1000000, "currency": "USD", "at": "2026-05-14T09:00:00Z" },
          { "external_id": "ext_def", "amount": 500000, "currency": "USD", "at": "2026-05-14T14:00:00Z" }
        ]
      }'
```

Matching is per currency and per amount within a time window. The response surfaces three sets: `matched`, `unmatched_external` (items with no posting to pair), and `unmatched_internal` (postings in the window that no external item claimed). The unmatched sets are your break list.

Runs are replayable. Matched postings are marked once with the external reference, and a re-run of the same snapshot excludes already-reconciled postings, so repeats are safe. Fetch a past run with its full snapshot:

```bash
curl "https://ledger.southpay.io/api/v1/reconciliation_runs/{id}" \
  -H "Authorization: Bearer $TOKEN"
```

For the comparison basis itself, the reports endpoints give you ledger-side totals to check against the external figures. Use the trial balance for per-currency debit and credit totals across every account:

```bash
curl "https://ledger.southpay.io/api/v1/reports/trial_balance?at=2026-05-14T23:59:59Z" \
  -H "Authorization: Bearer $TOKEN"
```

The trial balance is computed from `value_date`, so an "as of" figure is reproducible, and a healthy ledger shows a zero residual per currency.

<Info>
  External systems named here, such as a processor or a bank, are your own integrations. The ledger is your system of record for what the money means; reconciliation is how you prove it agrees with the systems that moved it.
</Info>
